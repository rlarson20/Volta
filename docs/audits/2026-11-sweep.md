# 2026-11 sweep: defects found by checking against PyTorch

Frozen record, like the other files in `docs/audits/`. Open work from it is in the GitHub issues (search the S-ID). Original text is never edited or removed; corrections are appended under `## Corrections` at the end (`.claude/rules/audits.md`).

**Method.** Three read-only audits (layers, core ops, optimizers/IO/data/examples) listed candidate defects from the code. Each one was then run, not just read:

- **Against PyTorch.** `scripts/torch_ref/gen_fixtures.py` (a `uv` script, `torch==2.15.0`, `just torch-fixtures`) writes f32 reference values to `tests/fixtures/torch/*.safetensors`. The `tests/torch_ref_*.rs` files load them with `volta::io::load_safetensors`. Regenerating gives byte-identical files. [corrected 2026-11-11: see C3]
- **Without PyTorch** where the answer is a hand calculation or documented behaviour: `tests/sweep_repros.rs`.
- **On the GPU**: `tests/gpu_sweep.rs`, run on an Apple M2. Every test prints `GPU-RAN <name>`, because a GPU test with no adapter returns early and reports `ok`.

A confirmed defect has an `#[ignore = "S<n>: ..."]` test that asserts the correct answer and fails today (invariant 6). `cargo test --no-default-features --test <file> -- --ignored` shows the numbers below.

**Result.** 22 reference tests pass against PyTorch (and the Muon/SGD/Adam trajectories among them), and 38 tests are `#[ignore]`d defects: 31 CPU (`--no-default-features`) and 7 GPU, all of which fail today with 0 passing, so none is a stale ignore. Fixtures regenerate byte-identically. [corrected 2026-11-11: see C3] `cargo clippy --all-targets -D warnings` is clean with and without default features, and `check-fallbacks` and `cargo fmt --check` pass. `just ci` and `just test-gpu` as a whole were not run; only the new test targets were.

Status key: ✅ confirmed by a failing test, ❌ refuted, 🟡 confirmed but different from the claim, ⚪ not run this round.

## What already matched PyTorch

These are live (not ignored) tests, the first external-reference coverage in the repo. The existing `tests/parity_*.rs` only compare the GPU with Volta's own CPU code.

| Area | Checked | Tolerance |
| --- | --- | --- |
| `sum_dim`, `mean_dim`, `softmax`, `log_softmax` | forward and weighted gradient, every axis of a `[3,4,5]` input | 1e-5 / 1e-4 |
| `SGD` (plain; momentum 0.9 + weight decay), `Adam` (+ weight decay) | 5 steps, fixed gradients | 1e-5 |
| `Muon` (wide 2x3, tall 3x2) | 5 steps, fixed gradients | 1e-4 |
| `Linear`, `LayerNorm`, `GELU` | forward, gradients of input and parameters | 1e-5 / 1e-4 |
| `Conv2d` (stride 2, pad 1), `ConvTranspose2d` (stride 2, pad 1), `MaxPool2d` | forward, gradients | 1e-4 / 1e-3 |
| `BatchNorm2d` | train output, gradients, running mean/var after one step, eval output | 1e-5 / 1e-4 |
| `matmul` 2-D, batched 3-D, rank 4 with a broadcast batch dim | forward, gradients | 1e-4 / 1e-3 |
| `permute` (3-cycle), `PixelShuffle` | forward, gradients | 1e-5 / 1e-4 |

The Muon expected values are a float32 transcription of `torch.optim.Muon`'s step. torch runs Newton-Schulz in **bfloat16**, which is about 1% off a float32 implementation (measured: 2.7e-4 on a 0.38 parameter after one step), so it cannot be a tight reference. The generator asserts the transcription stays within 5e-3 of `torch.optim.Muon` for all five steps.

## Refuted or narrower than claimed

- ❌ **"Backward twice over `x * x` gives 18 (torch 12)."** It gives 12. The root is only seeded, never accumulated into, so a graph with no intermediate node is exact. S1 needs an intermediate (`sum(2a)`), and `second_backward_on_a_graph_with_no_intermediate_node_is_exact` pins the good case. The existing `backward_twice_accumulates` still only asserts `>`.
- 🟡 **`I8` safetensors "panics on a byte length not divisible by 4."** Only the 4-byte case was run (it loads as the wrong shape, S18). The panic path is ⚪.
- 🟡 **"`matmul` rejects rank 3 @ rank 2."** True (`torch_ref_layers::matmul_batched_by_matrix_*`, "operands must have equal rank"), but it is a documented design limit (D6), not a silent error.
- 🟡 **`optimizer_step.wgsl` and the elementwise shaders bound the loop by `arrayLength` of a power-of-2 pool bucket.** No wrong result was demonstrated: the extra threads write only the unused tail. It is wasted work and up to 2x VRAM, not a correctness defect, so it stays a performance note.

## Not run this round (⚪)

- S13 (`Sequential::to_device` skips a child's `to_device`): needs a `PositionalEncoding` in a `Sequential` on the GPU.
- Negative momentum on the GPU SGD path (`sgd.rs:35,119`); SGD folding `lr` into velocity (latent until `set_lr`); Adam with `beta1 = 0` on the GPU.
- MNIST header overflow (`mnist.rs:32`); `DataLoader` with `batch_size = 0`.
- README snippets that use `.borrow()`, the GPU snippet's `NoGradRequired`, and the zero-copy safetensors claim; `layernorm_demo` checking zero gradients; `char_language_model`'s `temperature`; `dcgan`'s missing detach.
- `LSTMCell` and `MultiHeadAttention` against torch with loaded weights (`MultiHeadAttention` would first need S10/S11 decided, since its residual is part of the output).
- `time_sequence.rs` calls `backward()` once per timestep, so S1 applies to it; the size of the effect was not measured.

## Design divergences (not bugs; document, do not fix)

- **D1.** Default initializations differ from PyTorch: `Linear` Xavier uniform with zero bias (torch: U(±1/√in), random bias), `Conv2d`/`ConvTranspose2d` He normal with zero bias, `LSTMCell` Xavier with zero biases, and `MultiHeadAttention` q/k/v with no bias.
- **D2.** `Embedding` initializes U(±0.1) and its comment called that "PyTorch default"; torch's default is N(0,1). The comment is corrected in this change.
- **D3.** `Linear.weight` is `[in, out]` (torch `[out, in]`), so a square torch checkpoint loads without error and transposed. `StateDictMapper::transpose_linear` is the route.
- **D4.** State-dict keys are `gamma`/`beta` for norm layers (torch `weight`/`bias`); BatchNorm has no `num_batches_tracked`; LayerNorm stores gamma flattened.
- **D5.** Missing options: dilation, groups, `output_padding`, `ceil_mode`, `padding_idx`, BatchNorm `affine`/`track_running_stats`, `(N,C,L)` input to `BatchNorm1d`.
- **D6.** `matmul` needs equal operand ranks and rank >= 2 (torch broadcasts, and accepts 1-D); 1-D @ 1-D is not supported.
- **D7.** `DType::promote` disagrees with torch for F16/BF16 with integers, and nothing calls it.
- **D8.** Muon's momentum is `v = μv + g`, torch's is `lerp`; the two differ by the constant `1/(1-μ)`, which the Frobenius normalization removes for matrices (the trajectory tests confirm this). Rank-1 parameters go through plain momentum here and through AdamW in the reference.

## Corrections

Appended after the original text, which is unchanged (`.claude/rules/audits.md`).

### C1 (2026-11-10): S24 starts lower than 45, and fails in two stages

- **Said** (S24 row): "GPU `tanh` returns NaN for x >= 45 (44 is fine; negative inputs saturate to -1). It is the f32 overflow of `exp(2x)`."
- **True:** on the Apple M2, GPU `tanh` is correct up to 43.65, returns **0** (CPU: 1) for about 43.7 to 44.35, and NaN from 44.37. So 44 was not fine. Negative inputs are fine, as stated, and the repro (`tanh([-100,-50,50,100])` gives `[-1,-1,NaN,NaN]`) is as reported.
- **Why:** Metal computes `tanh` as `(e^2x - 1) / (e^2x + 1)` under fast math. The fast divide flushes to 0 once the denominator passes 2^126 (x about 43.67), and `e^2x` overflows to `inf` at x = 44.36, giving `inf / inf = NaN`. The overflow named above is the second stage, not the first.
- **Evidence:** a probe on the M2 (2026-11-10, run while working #49) printed `tanh(x)` of 1 at 41, 42, 43, 43.5 and 43.6, 1.0000001 at 43.65, 0 at 43.7, 44, 44.3 and 44.35, and NaN at 44.37 and 45.
- **Fix:** PR #146 (`Fixes #49`). That PR removes the S24 `#[ignore]`, whose reason text also said "44 is fine".

### C2 (2026-11-11): S8's repro compared probability targets against torch's class-index answer

- **Said** (S8 row): "`cross_entropy_loss` multiplies one-hot targets by log-probs. A `-inf` logit on a non-target class: NaN vs 1.0838."
- **True:** the defect is real for **class-index** targets, which Volta turned into one-hot weights and multiplied, so `0 * -inf` made the loss NaN where torch's gather gives 1.0838. The repro (`torch_ref_ops::cross_entropy_with_neg_inf_off_target_logit_is_finite_like_torch`) passed Volta float one-hot (probability) targets instead, and compared the result against torch's class-index answer. For probability targets torch also multiplies, and returns NaN on these logits, so Volta's NaN there matched torch.
- **Evidence:** `torch==2.15.0`: `F.cross_entropy(z, torch.tensor([0, 1]))` is 1.0838 and `F.cross_entropy(z, one_hot([0, 1], 3).float())` is NaN, for `z = [[1, -inf, 2], [0.5, 0.2, -inf]]`. Both are now fixture entries (`ce_neginf.out`, `ce_neginf.probs_out`).
- **Fix:** the PR for #42 passes class indices in the repro and adds a probability-target test that expects NaN.

### C3 (2026-11-11): fixtures regenerate byte-identically only on the platform that wrote them

- **Said** (Method): "Regenerating gives byte-identical files." (also in Result: "Fixtures regenerate byte-identically.")
- **True:** on Linux x86_64, `just torch-fixtures` rewrites all twelve files. The CPU wheel reports `torch.__version__` as `2.15.0+cpu`, not `2.15.0`, which changes the metadata. And seeded `torch.randn` draws differ: in `reductions`, the input `x` and every value derived from it change. The `ops` group, whose inputs are written out by hand, regenerates tensor-for-tensor identical. Whether it holds on the machine that wrote the committed files (whose torch reports `2.15.0`) was not checked here. Since #42, `ops.safetensors` itself was written on Linux and records `2.15.0+cpu`.
- **Evidence:** a cloud session (Linux x86_64, `uv run scripts/torch_ref/gen_fixtures.py`, 2026-11-11, working #42): all twelve files differ from `HEAD`; a tensor comparison of `reductions` lists 24 changed keys, `x` among them; `ops` has none changed.
- **Fix:** none yet. This answers #152's open question (byte-stable on a Linux runner? No); a fixture check there needs a tolerance, and the committed files can only be reproduced on the original platform.
